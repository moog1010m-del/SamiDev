# قياس تأخير شات المساحات — 17 أكتوبر 2026

## النتيجة وحدودها

اختبار الكود الحالي على بوابتين HTTP مستقلتين، PostgreSQL فعلية وRedis فعلية، مع حسابين مستقلين لكل مساحة من المساحات الأربع:

| الحالة | العينات | وسيط ظهور الرسالة | ظهور الرسالة عند p95 | أقصى ظهور |
|---|---:|---:|---:|---:|
| بث SSE مع حظر طلبات تاريخ الشات في المتصفح | 64 | 31ms | 54ms | 69ms |
| نفس الكود مع تعطيل EventSource عمدًا وترك التحديث كل 3 ثوانٍ | 8 | 2095ms | 2600ms | 2600ms |

تُقاس المدة من استدعاء fetch الخاص بإرسال النص إلى أول MutationObserver يؤكد ظهوره في DOM المتصفح الآخر. تُسجّل أيضًا لحظة حدث SSE وعودة ترويسات تأكيد HTTP. أكد الخادم جميع الرسائل الـ72 برد 200، وكل الرسائل الـ64 في الحالة الأولى وصلت بحدث message حي، لا بلقطة تاريخ. أُعيد الاختبار بعد اكتمال التغييرات. كانت النتائج السابقة القريبة (31/60/147ms) متوافقة مع النتيجة النهائية؛ الأرقام محلية وليست ضمانًا لزمن الإنترنت أو لاختبار ضغط 150 عضوًا.

هذه مقارنة سببية مضبوطة: تعطيل البث وحده أعاد تأخير الثانيتين والثلاث. لا تثبت أين يتعطل البث على موقع المستخدم بدون عنوانه وإصداره ونتيجة اتصال /events لديه. يجب فصل بطء الحفظ، ورفض/انقطاع SSE، وتجميع الوكيل، وتأخر الرسم. لم نُجرِ اختبار جهاز Flutter فعلي أو نفق الموقع العام في هذه التجربة. يشغّل الاختبار معالجات HTTP الحقيقية؛ دورة تشغيل محرك المباريات ليست ضمنه.

## عطل مستقل ظهر عند استخدام PostgreSQL

قبل إصلاح قفل القبول، فشل POST دخول المساحة برمز 500 والاستثناء:

```text
RuntimeError: Transaction accessed an unlocked social key
```

كان `RoomPolicy.transaction` يستخدم معاملة مستندات محجوزة على مفتاح القبول وحده. داخلها، يحتاج حساب سعة المساحة وقراءة صلاحيات العضو إلى قراءة مفاتيح حسابات أخرى؛ حارس المعاملة يرفضها بحق. لم تكشف اختبارات Memory/Redis هذا التعارض. هذا عطل دخول مثبت، وليس إثباتًا أنه سبب تأخير رسائل الموقع العام.

أصبح قفل القبول قفل PostgreSQL advisory transaction مستقلًا عن معاملات المستندات، عبر مجمع كسول بسعة اتصال واحد لكل بوابة. عمليات الحسابات تحتفظ بمعاملاتها وأقفال مفاتيحها الأصلية. الفصل يمنع حراس معاملات المستندات من رفض قراءات العضوية، ويمنع طالبي الدخول المنتظرين من استهلاك مجمع المستندات وحجب اتصال يحتاجه حامل القفل. تكلفة السعة: حتى اتصال PostgreSQL إضافي واحد لكل بوابة عند الحاجة؛ لا تغييرات في قواعد الألعاب أو بروتوكول الحركات.

## التحقق من السلامة

جميع الاختبارات التالية نجحت:

- الاختبار الجديد ببوابتين ومجمع مستندات مقيد عمدًا باتصال واحد: حد الأعضاء عند دخول متزامن، منع الحساب من طاولتين، حد الطاولات، بداية المباراة وحفظ مهلة الانتظار عبر البوابتين، ورفض قراءة مفتاح مستند غير مقفول داخل معاملة مستندات.
- قياس البث والاسترجاع بالمتصفح المذكور أعلاه، بلا أخطاء JavaScript وبلا استخدام polling في حالة البث.
- `postgres_read_concurrency.py`: قراءة committed دون حجز، رؤية تحديثات المعاملة نفسها، 50 زيادة رصيد ذرية، ورؤية الحظر فورًا.
- `room_policy_redis.py`: قواعد القبول والمغادرة والتزامن وPub/Sub مرة واحدة لكل بوابة على Redis فعلية.
- `community_chat_security_v18_regression.py`: سياسة النصوص ومصدر الطلب وحدود الإرسال.

## إعادة التشغيل

استخدم قاعدة اختبار PostgreSQL وRedis محليتين، مع قيم الربط عبر بيئة الاختبار. لا تضف الأسرار للمستودع. الاختبار يستخدم بادئات عشوائية ويحذف مستنداته ومفاتيحه فقط، ولا يستخدم FLUSHDB أو TRUNCATE.

```bash
SAMIDEV_CHAT_DIAGNOSTIC_DIR=/tmp/samidev-chat-diagnostic \
python tests/postgres_community_latency.py
```
