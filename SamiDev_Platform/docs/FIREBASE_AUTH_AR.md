# مصادقة Firebase — تجهيز محلي وتفعيل لاحق

الحالة: الكود مجهز للويب وFlutter، والميزة **مغلقة افتراضيًا** (`SAMIDEV_FIREBASE_AUTH=0`). لم يُربط هذا التعديل بمشروع Firebase فعلي. اختبارات المزود تستخدم بدائل داخل الاختبارات فقط؛ التحقق الإنتاجي يعتمد Firebase Admin SDK ولا يقبل هوية يرسلها العميل دون التحقق من التوقيع.

## السلوك

- يبدأ اللاعب كضيف بجلسة لعب محلية. من الإعدادات ينشئ حسابًا ببريد إلكتروني وكلمة مرور أو يتابع باستخدام Google، دون طلب اسم مستخدم. لا يُربط البريد ولا تُصدر جلسة الحساب المرتبط قبل توثيق البريد؛ جلسة الضيف مستقلة وتسمح باللعب قبل الربط.
- دخول: البريد وكلمة المرور لدى Firebase، ثم يتحقق الخادم من ID token ويُصدر جلسة المنصة المعتادة. أسماء اللاعبين والغرف والأرصدة والمقتنيات والصلاحيات تبقى في PostgreSQL.
- إنشاء الحساب بالبريد يطلب تأكيد كلمة المرور ويمنع الإرسال عند عدم تطابقها. حقل التأكيد لا يُرسل إلى Firebase أو الخادم، ولا يظهر عند الدخول أو توثيق البريد.
- الاستعادة: رسالة إعادة تعيين كلمة المرور من Firebase. لا يوجد سؤال سري أو SMS. يفتح اللاعب رابط Firebase في البريد ثم يعود للتطبيق.
- Flutter يستخدم شاشة Dart أصلية وطلبات HTTPS؛ لا يحتاج WebView للتسجيل أو الدخول. الرسائل تُفتح خارج التطبيق في تطبيق البريد/المتصفح.
- الويب يستخدم ملف JavaScript محليًا وواجهات Google REST الرسمية؛ لا يُحمّل Firebase JavaScript من CDN. Google هو مزود المصادقة الخارجي عند التفعيل، وليس نظامًا محليًا بالكامل.

## إعداد مشروعك لاحقًا

1. أنشئ مشروع Firebase تجريبيًا، وفعّل Authentication → Email/Password. فعّل حماية تعداد البريد الإلكتروني واضبط سياسة كلمة المرور **Require** بحد أدنى 8 وحد أقصى 128 حرفًا، بما يتوافق مع الواجهات.
   إذا كان المشروع مستخدمًا بالفعل بسياسة 15 حرفًا، عدّل **Authentication → Settings → Password policy → Minimum length** إلى **8** أيضًا؛ تغيير واجهة التطبيق وحده لا يغيّر سياسة Firebase. لا توجد بيانات اعتماد لإدارة مشروعك الفعلي ضمن هذا التعديل.
2. أضف نطاق موقعك إلى Authorized domains، وراجع قوالب توثيق البريد وإعادة تعيين كلمة المرور واسم المرسل. يمكن استخدام صفحات إجراءات البريد الافتراضية المستضافة لدى Firebase؛ لا يلزم بناء صفحة استعادة جديدة.
3. خذ **Project ID** و**Web API Key** الخاصين بالمشروع نفسه. المسار الحالي يعتمد REST، لذلك لا يحتاج `firebase_options.dart` أو ملفات Google المضمنة في Android/iOS ولا `authDomain`/`appId`. المفتاح العام ليس مفتاح حساب الخدمة. قيوده يجب أن تسمح بخدمتي Identity Toolkit وSecure Token وبعملاء الويب وFlutter المستخدمين؛ اختبر القيود فعليًا قبل التفعيل.
4. امنح الباك اند صلاحية قراءة مستخدمي Firebase باستخدام Application Default Credentials في بيئة الخادم. إن احتجت ملف حساب خدمة، احفظه خارج المستودع وسياق Docker build، واجعل `GOOGLE_APPLICATION_CREDENTIALS` يشير إليه. لا تضعه في `game/` أو Flutter أو Git أو المحادثات. SDK يحتاج الوصول لخدمات Google وشهادات توقيع الرموز، وليس API key وحده.
5. ثبت متطلبات `backend/requirements.txt`. في إعداد البيئة المحلية ضع:

```dotenv
SAMIDEV_FIREBASE_AUTH=1
SAMIDEV_FIREBASE_PROJECT_ID=YOUR_FIREBASE_PROJECT_ID
SAMIDEV_FIREBASE_API_KEY=YOUR_PUBLIC_WEB_API_KEY
```

هذه أمثلة فقط؛ لا توجد إعدادات فعلية مضمنة. حافظ على PostgreSQL وRedis وHTTPS وإعدادات Origin الحالية. في الإنتاج تُضبط القيم وبيانات اعتماد المزود نفسها لجميع الـ gateways ثم يُعاد تشغيلها معًا لتجنب اختلاف طريقة الدخول بين الخوادم.

### عند استخدام Docker

الملف الأساسي يمرر إعدادات Firebase العامة لجميع الـ gateways، لكنه **لا ينسخ بيانات اعتماد إدارية**. على جهازك يمكن إنشاء override محلي خارج المستودع وفق إعدادات النشر لديك، مثل:

```yaml
x-firebase: &firebase
  environment:
    GOOGLE_APPLICATION_CREDENTIALS: /run/secrets/firebase-admin.json
  volumes:
    - /absolute/private/firebase-admin.json:/run/secrets/firebase-admin.json:ro
services:
  gateway1:
    <<: *firebase
  gateway2:
    <<: *firebase
  gateway3:
    <<: *firebase
```

يُدمج مع `docker-compose.yml` باستخدام `-f` لكلا الملفين. مسار المصدر يُستبدل بمسار خاص خارج سياق البناء. اجعل الملف قابلًا للقراءة لمستخدم الحاوية فقط. يمكن بدل الملف استخدام هوية عمل مناسبة وADC عند الاستضافة المدعومة.

## بداية جديدة

الحسابات المحلية القديمة اختبارية ولا يوجد مسار لترحيلها أو ربطها بكلمة مرورها. ربط الضيف الجديد من جلسته مسار مستقل. عند تفعيل Firebase:

- التسجيل والدخول من الويب وFlutter يدعمان البريد وكلمة المرور أو Google. الحساب الجديد يُربط بالضيف الحالي تلقائيًا ويحفظ اسمه وتقدمه. إن لم توجد جلسة ضيف يُولَّد اسم عشوائي فريد. يمكن تغيير الاسم اختياريًا من إعدادات الحساب، وتبقى المرة المجانية غير مستهلكة عند الربط.
- مسارا الدخول والتسجيل المحليان يرفضان الطلبات، والجلسات المحلية القديمة لا تمنح دخولًا؛ جلسات الضيف الجديدة مسموحة. لا يظهر زر «الدخول بالطريقة القديمة» ولا يوجد ربط باستخدام كلمة مرور حساب قديم.
- كل Firebase UID موثق يرتبط بهوية لاعب واحدة؛ الهوية المحفوظة تفتح حسابها الأصلي دون دمجه مع الضيف. الإعادة المتزامنة أو تكرار الدخول لا ينشئان ملفات مكررة.
- البيانات الاختبارية الموجودة لا تُحذف أو تُدمج أو تُعاد أرصدتها تلقائيًا. أسماؤها تظل محجوزة، فاختر أسماء جديدة أثناء الاختبار. تنظيف قاعدة الاختبار خطوة مستقلة عند الحاجة.
- ما دام المفتاح `SAMIDEV_FIREBASE_AUTH=0`، يبقى نظام التطوير المحلي السابق متاحًا إلى أن تُكمل إعداد Firebase.

### إعداد أول مشرف

أنشئ حسابك في Firebase ووثّق بريده. خذ **UID** من Firebase Console وضعه في إعدادات الخوادم الثلاثة:

```dotenv
SAMIDEV_FIREBASE_ADMIN_UID=YOUR_VERIFIED_FIREBASE_UID
```

في الدخول التالي يحصل صاحب هذا UID الموثق على دور admin، سواء كان ملفه المحلي جديدًا أو موجودًا. القيمة لا تُرسل للواجهة، ولا يعتمد منح الصلاحية على اسم المستخدم أو البريد أو حقل role في الطلب. بعد منح الصلاحية أزل هذا المتغير من إعدادات الخوادم وأعد تشغيلها؛ يبقى الدور محفوظًا وتُدار الصلاحيات بعدها من المنصة. لا تترك قيمة bootstrap بعد الإعداد حتى لا تعيد منح الدور إن سحبته لاحقًا.

عند تفعيل Firebase تُتجاهل إعدادات المشرف المحلي `SAMIDEV_ADMIN_USERNAME/PASSWORD` ولا يُنشأ منها حساب إضافي.

## الجلسات والصلاحيات

- الخادم يستخدم SDK الرسمي للتحقق من التوقيع والمشروع وانتهاء الرمز وإلغائه (`check_revoked=True`) والبريد الموثق. دور المشرف مصدره قاعدة المنصة؛ طلب التسجيل لا يمنح أدوارًا أو رصيدًا.
- جلسة المنصة تستخدم Cookie بـ HttpOnly وSameSite وSecure على HTTPS. Flutter يحفظ جلسة المنصة فقط في مخزنه الآمن. رموز Firebase المؤقتة في ذاكرة الواجهة وتُمسح بعد الدخول أو تبديل الطريقة، ولا تُحفظ في localStorage.
- جلسات Firebase تفحص تعطيل الحساب وتوثيقه ووقت إلغاء رموزه. التخزين المؤقت للنتيجة مدته 30 ثانية؛ ليس الإلغاء فوريًا في كل اتصال. الفحص التالي بعد انتهاء المهلة يرفض الجلسة الملغاة. التطبيقات المفتوحة تعتمد كذلك دورة التحقق القائمة للاتصال.
- تعذر الاتصال بالمزود ينتج 503 ولا يتحول إلى قبول جلسة أو حذفها باعتبارها كلمة مرور خاطئة. قد يمنع هذا الوصول مؤقتًا عند تعطل Firebase.
- الربط محفوظ في PostgreSQL تحت namespace `firebase`، وليس Redis وحده. Redis يبقى مسؤولًا عن الجلسات والتذاكر ومحددات الطلبات المؤقتة.
- حسابات Firebase الجديدة لا تملك كلمة مرور محلية. إيقاف الميزة يعيد وضع الاختبار المحلي فقط ولا يتيح دخول حسابات Firebase بكلمة مرور محلية. تغيير مشروع Firebase لاحقًا يحتاج ترحيل هوية مخططًا له.

## اختبارات قبل التفعيل العام

الاختبارات المحلية المنفذة تغطي توثيق الهوية، رفض البريد غير الموثق، رفض ربط البيانات الاختبارية، تنافس إنشاء الحساب بين خادمين ومنح صلاحية المشرف عبر UID موثق فقط، بقاء البيانات بعد فقدان مفاتيح Redis، رفض الجلسة الملغاة وتعطل المزود، ومراحل الواجهة في Chromium وFlutter. هي لا تثبت وصول البريد الحقيقي أو إعداد مشروع Google أو قدرة 10 آلاف لاعب.

بعد إضافة إعداداتك شغّل في بيئة تجريبية بحسابات اختبار:

- تسجيل جديد → رسالة توثيق فعلية → دخول من الويب ومن هاتف Flutter.
- شراء عناصر بحساب Firebase جديد ثم الدخول من جهاز ثانٍ → تحقق من نفس هوية اللاعب ومقتنياته. جرّب الدخول بكلمة مرور حساب اختباري قديم وتأكد من رفضه.
- استعادة كلمة المرور → تأكد من رفض الكلمة القديمة والجلسات السابقة بعد مهلة الفحص، ونجاح الجديدة.
- تعطيل حساب في Firebase → رفض دخوله وجلساته، مع بقاء صلاحيات المشرفين المحلية كما هي.
- تسجيل خروج ودخول متكرر مع انقطاع الشبكة، واختبار حدود الطلبات والرسائل.

ابدأ بالبريد وكلمة المرور دون SMS. راجع صفحة Firebase Authentication limits وPricing عند التفعيل؛ للحسابات والرسائل حدود استخدام تختلف بحسب الخطة. لا نفترض أن الخطة المجانية تستوعب أي حجم أو أن هذا التعديل يمنح جاهزية إنتاج تلقائية.

### تشغيل الاختبارات المحلية

من `SamiDev_Platform` وبايثون مثبتة عليه متطلبات الباك اند:

```bash
python tests/firebase_auth_regression.py
python tests/firebase_auth_browser.py
```

اختبار PostgreSQL يحتاج `SAMIDEV_TEST_DATABASE_URL` و`SAMIDEV_TEST_REDIS_URL` لقاعدتي اختبار. يُظهر skip صريحًا عند غيابهما؛ بقية الاختبارات لا تستخدم Google. اختبار المتصفح يحتاج Chromium وPlaywright ويمكن تحديد مسار وحدته عبر `SAMIDEV_PLAYWRIGHT_MODULE`.

من `SamiDev_Flutter`:

```bash
flutter test --no-pub
flutter analyze --no-pub --no-fatal-infos
```

إثبات الربط الفعلي والبريد وإصدارات Android/iOS يبقى خطوة لاحقة على جهازك بعد الإعداد.

## نتيجة التحقق لهذا التعديل

- 10 اختبارات مصادقة ناجحة، بما فيها الاختبار الفعلي على PostgreSQL وRedis؛ دون اختبارات متخطاة في التشغيل المنفذ.
- 26 اختبار Flutter ناجح. تحليل Dart نجح دون errors أو warnings، مع 12 ملاحظة info سابقة خارج الإضافة.
- Chromium: إنشاء حساب، حالة البريد غير الموثق، حساب جديد دون خيارات ترحيل، دخول وخروج، طلب استعادة، إكمال اسم مستخدم جديد، وحالة تعطيل Firebase/تعذر تحميل الإعدادات.
- اختبارات الدخول الحالي خلف وكيل HTTPS والمتجر نجحت، وملف Docker Compose اجتاز فحص التكوين. لم يُنشر أو يُعد تشغيل خدمات المستخدم.
- تمت مزامنة أصول الواجهة مع حزمة Flutter. لم تتغير ملفات محركات الألعاب.
- لم يتم اختبار مشروع Firebase فعلي أو توصيل بريد حقيقي أو بناء APK/IPA في هذا التعديل.

## دخول الضيف واستخدام البريد من الإعدادات
- المنصة تبدأ بجلسة ضيف تلقائية عند عدم وجود جلسة. `POST /api/auth/guest` يعيد اللاعب الحالي إذا كانت جلسته صالحة، ولا ينشئ حسابًا جديدًا عند كل تحميل. يخزن ملف اللاعب في PostgreSQL والجلسة في Redis. لا توجد كلمة مرور مشتركة للضيوف، ولا طلب Firebase لكل ضيف.
- الويب يعرض المساحات مباشرة. إعدادات الحساب موجودة في محرر الملف الشخصي. بفلاتر يوجد زر إعدادات الحساب أعلى المساحات، وواجهة إعداداته أصلية.
- إنشاء حساب ببريد جديد من الإعدادات يرسل `linkGuest=true` مع توكن Firebase موثّق. الباك إند يعتمد هوية الضيف من جلسته فقط، ويربط UID بنفس معرف اللاعب، فتظل المقتنيات والرصيد والإحصاءات والصلاحيات مرتبطة به. يرفع `authVersion` ويلغي صلاحية جلسات الضيف السابقة ثم يصدر جلسة حساب جديدة.
- الدخول ببريد مرتبط مسبقًا يفتح حساب ذلك البريد بعد تأكيد واضح بالواجهة. لا يجري دمج تقدم الضيف مع حساب آخر. محاولة الربط ببريد مرتبط ترفض بمعاملة واحدة دون سلب حساب أو نقل مقتنيات.
- حالة الإيميل غير الموثق تظل مرفوضة. الربط الفعلي وإرسال البريد يحتاجان تفعيل Firebase وإعداد الاعتماد بالمشروع؛ الاختبارات الآلية تحاكي استجابات Google ولا تثبت وصول رسالة حقيقية.
- الضيف غير المربوط يعتمد على حفظ الجلسة بالجهاز. مسح بيانات المتصفح/التطبيق أو انتهاء الجلسة قد يمنع استرداده؛ واجهة الإعدادات تشجعه على ربط البريد لحفظ الوصول.

## اسم واحد وتغيير الاسم
- `username` هو الاسم المعروض دون بادئة `@`. لا يوجد اسم ظاهر مستقل؛ يبقى حقل `displayName` في بروتوكول الألعاب للتوافق، لكن قيمته المعروضة هي اسم المستخدم.
- التغيير المجاني مرة واحدة لكل معرف لاعب. بعدها يحتاج `rename_card`؛ سعره الابتدائي 100 كوينز من العملة الحالية، وليس شراء مال حقيقي. يمكن تكرار شرائه، وتخزن الكمية في `renameCredits`؛ ليست قطعة تجهيز.
- الاسم 3–20 حرفًا إنجليزيًا أو رقمًا أو `_`، ويُحجز دون اعتبار حالة الأحرف. لا تُستهلك بطاقة إذا كان الاسم محجوزًا/غير صالح أو لم يتغير. تغيير حالة الأحرف وحده تغيير محسوب.
- `PATCH /api/profile` بحقل `username` يغيّر اسم المستخدم والاسم المعروض والفهرس في معاملة واحدة، ويسجل التغيير. حقل `displayName` القديم يمر بالقواعد نفسها لمنع تجاوز المجانية والبطاقات.
- تهيئة اسم الحساب عند ربط البريد لأول مرة ليست شراء تغيير، ولا تعيد تعيين سجل التغيير المجاني أو رصيد البطاقات. هوية الأصدقاء والمقتنيات والمباريات تعتمد معرف اللاعب الثابت.

## Google

فعّل Google من Sign-in providers وأضف نطاق الويب إلى Authorized domains.
الويب يستخدم حزمة Firebase الرسمية محليًا ونافذة المزود الرسمية؛ لا يحفظ جلسة
Firebase في localStorage. إصدار جلسة المنصة والتحقق من الهوية يظلان على الخادم.
زر Google لا يحتاج إدخال كلمة مرور SamiDev أو بريد يدوي. الهوية الجديدة تختار
اسم مستخدم ثم تربط الضيف؛ الهوية المرتبطة مسبقًا تفتح حسابها دون دمج تقدم الضيف.

لفلاتر أضف Android وiOS إلى Firebase وسجّل بصمات توقيع Android وأكمل إعداد
URL scheme الخاص بـ iOS. مرّر معرّفات OAuth العامة في
`SAMIDEV_GOOGLE_WEB_CLIENT_ID` و`SAMIDEV_GOOGLE_IOS_CLIENT_ID`؛ تمررها حاويات
الخوادم الثلاثة تلقائيًا. الخطوات مفصلة في
[تعليمات Google](../tools/firebase-web/README.md).
اختبارات المستودع تحاكي رد المزود؛ الاختبار بحساب حقيقي وعلى الأجهزة يتطلب
إعدادات المشروع الفعلية وإعادة بناء التطبيق.
