# اختبار رحلة ٥٠٠ لاعب

يشغّل `tools/player_journey.py` حسابات حقيقية عبر واجهات HTTP وWebSocket، على PostgreSQL وRedis محليين، مع ثلاث بوابات وثلاثة GameHosts افتراضيًا. لا يزرع حسابات أو عملات أو نتائج، ولا يقرأ أوراق الخصم من الخادم. يتخذ كل لاعب قرارات أونو من نسخة العميل الأصلية وحالته المسموح بها.

## السيناريو

1. تسجيل ٥٠٠ حساب، تسجيل الخروج والدخول والتحقق من إبطال الجلسة القديمة.
2. إرسال رسائل المجتمع والتحقق من وصولها لحساب آخر.
3. بدء ٢٥٠ مباراة متزامنة فعلًا، والتحقق من الدور والتسلسل لدى الطرفين بعد كل حركة، ومن وصول شات المباراة للطرفين.
4. إكمال خمس جولات طبيعية: ١٢٥٠ مباراة، والتحقق من مكافآت كل حساب بعد كل جولة. تتضمن الجولة الثانية إعادة اتصال عبر بوابة مختلفة.
5. شراء شارات متنوعة وتجهيزها، ومحاولة شراء مزدوجة للتأكد من الخصم مرة واحدة، وشراء نجوم، والتحقق من البروفايل العام والرصيد وسجل العمليات.
6. مباراة سادسة لكل حساب، للتأكد من توقف المكافآت عند الحد اليومي؛ ثم إعادة الدخول والتحقق من استمرار البيانات وإحصاءات اللعب والفوز.

مع `--browser-sample` يفحص Chromium بحجم هاتف المعاينة والإلغاء دون خصم، ثم تأكيد شراء فعلي بالعملات المكتسبة. هذه عينة واجهة واحدة، وليست ٥٠٠ متصفح أو أجهزة Flutter.

## التشغيل

من مجلد `SamiDev_Platform`، يلزم Node وPython مع اعتماديات الباك إند و`aiohttp` و`asyncpg` و`redis`، وخدمتا PostgreSQL وRedis للاختبار على loopback. للمتصفح يلزم Chromium و`playwright-core`.

```bash
export SAMIDEV_TEST_DATABASE_URL='postgresql://USER:PASSWORD@127.0.0.1:5432/TEST_DATABASE'
export SAMIDEV_TEST_REDIS_URL='redis://127.0.0.1:6379/6'
export SAMIDEV_PLAYWRIGHT_MODULE='/absolute/path/node_modules/playwright-core/index.mjs'
python tools/player_journey.py --players 4 --browser-sample --output /tmp/journey-4
python tools/player_journey.py --players 50 --output /tmp/journey-50
python tools/player_journey.py --players 500 --browser-sample --output /tmp/journey-500
node tests/player_journey_replica_regression.js
```

العدد يجب أن يكون زوجيًا. خيارات `--account-concurrency` و`--room-concurrency` تتحكم بالتدرج، و`--gateways` و`--hosts` بتوزيع الخدمات. زمن التفكير الافتراضي ٢٥–٧٥ مللي ثانية لتكثيف الحمل؛ ليس قياسًا لسلوك إنسان عادي. البذرة تضبط توقيت التفكير، ولا تثبت توزيع أوراق محرك اللعبة.

يشغّل الاختبار المصادقة وحدود الطلبات الحقيقية مع عناوين عملاء مختلفة محاكية عبر proxy موثوق داخل البيئة المحلية فقط. HTTPS ممثل بترويسة proxy؛ لذلك لا يختبر TLS أو الإنترنت الحقيقي. يرفض عناوين قواعد البيانات خارج loopback، ويستخدم مساحة مفاتيح منفصلة، وينظف بياناته وعملياته فقط، دون مسح شامل أو إعادة تشغيل الخدمات المشتركة. استخدم قواعد اختبار مخصصة؛ الحمل يؤثر في موارد الجهاز المشتركة.

## قراءة النتيجة

### نتيجة التشغيل الفعلي

في التشغيل المحلي على حصة ٤ أنوية و٣٢ GiB، اكتملت رحلة ٥٠٠ حساب: ١٥٠٠ مباراة، و٦١٬١٠١ حركة، و٣٠٠٠ فحص رصيد، و٥٠٠ شراء وتجهيز وفحص بروفايل وعودة للحساب، وعشر عمليات إعادة اتصال. نجحت عينة شراء Chromium. لم تسجل البوابات أخطاء مزامنة أو تحديد معدل أو مهلات إرسال.

النتيجة **`NO_GO` للأداء**: p50 للحركة ٨٤٫٣٩، وp95 **٢٨٣٫١٦**، وp99 ٤١٨٫٤٢ مللي ثانية؛ العتبة ٢٥٠. اجتازت الرحلة الوظائف المالية والمزامنة، لكن لم تجتز شرط الاستجابة. زمن مولد النسخ نفسه p95=١٣٫٩٥ مللي ثانية، والخدمات والمولد يتشاركون الجهاز؛ لا تنسب كل التأخير إلى الخادم ولا تعتبر هذه سعة جهاز إنتاج منفصل.

التشغيل الأول توقف عند تسجيل الحسابات بسبب استجابة `AUTH_BUSY` واحدة؛ حفظناه كذلك. التشغيل الكامل الثاني لم يحتج إعادة محاولة مصادقة. نجاح عينة ٥٠ لاعب كان p95=١٤٫٧٥ مللي ثانية. راجع [تقرير ٥٠٠ لاعب](tests/journey_reports/500_players.json) و[فشل التسجيل الأول](tests/journey_reports/500_initial_auth_busy.json). الخطوة التالية للتحسين قياس نفس الحمل بمولد مستقل وخدمات موزعة، ثم معالجة مسارات التأخير قبل رفع سقف العدد؛ لا تغيير العتبة لتسمية التشغيل ناجحًا.

عند `AUTH_BUSY` يعيد العميل طلب التسجيل أو الدخول ثلاث مرات كحد أقصى بتأخير متزايد؛ يسجل عدد الاستجابات في `auth_busy_responses`. هذه الاستجابة تسبق تنفيذ عمل كلمة المرور. لا يعيد تلقائيًا طلب الشراء أو الحركة أو أي عملية مالية. استنفاد المحاولات يفشل الاختبار، والنتائج تحفظ أيضًا التشغيل الفاشل الأول دون إعادة المحاولة للمقارنة.

يحفظ `report.json` وملف حركات لكل مباراة، ومع المتصفح تقريرًا وصورة لتأكيد الشراء. لا تحفظ التقارير كلمات المرور أو ملفات تعريف الارتباط أو تذاكر الاتصال. كود الخروج `0` يعني اكتمال السيناريو دون أخطاء ووصول p95 للحركة تحت العتبة المحددة بـ`--max-p95-ms`، وافتراضيها ٢٥٠ مللي ثانية. كود `2` يعني `NO_GO` ويحدد التقرير مرحلة الفشل.

`PASS_JOURNEY_PREPRODUCTION` نجاح لهذا السيناريو على هذه البيئة؛ لا يمنح شهادة إنتاج. يظهر `productionCertified: false` دائمًا. يلزم قبل اعتماد المنصة: اختبارات الفيزياء لكل الألعاب، أجهزة Flutter ومتصفحات أخرى، نشر TLS وشبكة واقعية، اختبار طويل، عواصف إعادة الاتصال، تعطل الخدمات واستعادة السجل، ومعالجة ملاحظات [مراجعة المزامنة والسعة](SYNC_CAPACITY_REVIEW_AR.md). نجاح ٥٠٠ لاعب لا يثبت قدرة ١٠ آلاف.

تقرير الرحلة يشمل زمن HTTP والحركة، وزمن عمل مولد العملاء نفسه، والحسابات والمباريات والمكافآت والمشتريات وأخطاء البروتوكول. تحفظ النتائج المختصرة المعتمدة في `tests/journey_reports`، وتبقى الآثار التفصيلية خارج المستودع لتجنب تضخيمه.
